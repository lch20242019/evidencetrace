日期: 2026-07-27

## 与原计划的关系

本轮对应 canonical v3.0 计划中的“真实文档 dogfood”路线。它验证公开 CLI 的
真实用户闭环:

```text
Markdown / ADR / RFC / README / Git diff
-> Claim Miner
-> bounded Audit Coordinator
-> citation verification 或按需 Scout
-> Claim Judge
-> bounded Coordinator review
-> conditional Challenger
-> Policy + terminal + SARIF + optional unapplied patch
```

本轮不创建数据集，不计算 F1 或 accuracy，不比较 Single Agent 与 Multi-Agent
优劣。Phase 3 继续为 `completed_with_known_limitations`，
`phase4_eligible=false`。

- Case 1 在 6 个 Miner 段落失败后仍完成 4 个 claim 和 1 次 Judge。
- Case 2 在 4 个 Miner 段落失败后仍处理两个 Scout 降级 claim。

- 没有全局 parse/config/artifact 崩溃；三次命令均返回受控 `partial`。
- Case 1 的 Coordinator review plan 被拒绝后使用 deterministic fallback，
  说明 Controller 拒绝权生效；具体拒绝原因不可观察。
- `needs_human` 和 `discovery_unavailable` 在 canonical verdict/SARIF 中被渲染为

- SARIF URI 均为 repo-relative，行号可操作，没有绝对路径或 secret。
- Patch 写入边界符合“只生成、不应用”，但本轮没有生成有内容的建议 patch，

## 问题分级

### P0: 发布阻塞

**真实 Miner 契约可靠性和诊断不足。** 17 个真实段落调用中 11 个只留下
`miner_error`；ADR 的核心版本决策和 PR 的唯一改动事实段落全部丢失。错误被隔离，
但用户看不到失败 stage/code，也无法区分“没有 claim”与“Agent 失败”。

复现:

```console
evidencetrace check README.md --changed-from HEAD
```

对固定 PR #871 输入得到 `partial`、0 claims 和 1 个 `miner_error`。

### P1: 下一轮 dogfood 前应调整

1. Provider observability 未进入产品 artifact，无法报告实际 attempts、schema
   recovery、tokens、latency 或安全失败分类。
2. `needs_human/discovery_unavailable` 被映射为 `not_in_source` SARIF warning，
   语义容易误导。
3. 唯一真实 Judge verdict 使用了真实 span，但 evidence 对 claim 支持偏弱，
   `entailed/0.85` 有过度确信风险。
4. Coordinator 完整 typed plan、plan rejection code 和 Scout query provenance
   未持久化，无法完成真实审计追踪。
5. Patch 安全边界已验证，但有内容的候选 patch 尚未验证。

### P2: 可用性与覆盖缺口

1. Inline-code stripping 使一个 event claim 丢失事件名和元素名。
2. Tavily 未配置，真实 Scout 的 query、candidate URL、safe fetch 和 evidence
   路径未验证。
3. 没有 verdict 进入高风险 review，真实 Challenger 未验证。
4. 从源码 checkout 运行，未验证 PyPI/`uvx` 安装和五分钟首次安装体验。

### P3: 记录项

- CLI `--version` 仍显示 `0.0.0`，发布前需要版本与 package metadata 收口。
- 标题和代码块-only diff 会正确产生 0 个 changed paragraph；用户文档需要说明
  这是预期选择语义。

## 是否扩展到 10 个案例

当前不建议。先完成以下最小修复并用新的真实文档做小规模复核:

1. 为 Miner 的 post-provider failure 提供安全、allowlisted stage/code，并让终端
   明确显示失败段落数。
2. 将 provider attempts、schema recovery、tokens 和 latency 汇总进
   `product_run.json`，不保存 prompt、reasoning 或原始响应。
3. 修正 `needs_human`/`discovery_unavailable` 的 Policy/SARIF 表达。
4. 在有 Tavily key 的受控环境验证一次真实 Scout，并选择能成功到达 verdict 的
   高风险文档验证 Challenger。
5. 生成至少一个非空候选 patch，继续证明输入和 Git index 不变。

这些条件完成后再决定是否扩大到 10 个案例；扩大仍是 dogfood，不得转化为新
holdout 或 formal gate。
